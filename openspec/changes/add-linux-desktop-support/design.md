# Approach

- Keep the CLI, route selection, YAML format and validation, and tray menu actions and state in the shared core. The core does not select a platform at runtime. Go selects each platform implementation at build time from `_windows.go` and `_linux.go` files (or build constraints for code shared by multiple operating systems).
- Keep the adapters at existing package boundaries rather than introducing a single `Platform` interface. `internal/config` resolves the configuration path; `internal/registration` provides `Register` and `Restore`; `internal/app` and `internal/autostart` handle desktop effects such as native tray integration, editing, source metadata, and sign-in startup. Use package-local functions for these boundaries; introduce an interface only where a caller needs interchangeable implementations or test doubles.
- Start with `config.Path()`: preserve the Windows executable-adjacent path and add Linux XDG resolution behind the same function. Keep the configuration directory and the executable directory distinct: keep `config.yaml` and its schema together in the former, and use that same YAML path for loading, watching, and editing; resolve relative browser executable paths from the latter. Do not silently migrate configurations from unofficial Linux builds.
- Add a Linux registration implementation in `internal/registration` selected by Go's Linux file suffix. Keep the Windows Settings flow intact; do not reuse its Windows-specific prompts or case-insensitive identifier comparisons for Linux desktop IDs. Limit Linux integration to a stable, application-owned desktop ID and the user-level XDG directories. Advertise both scheme handlers in a desktop entry with an absolute executable path and `%U`, encoded according to Desktop Entry rules, not shell quoting.
- Store the previous scheme IDs under `$XDG_STATE_HOME/dynamicbrowser/` (default `$HOME/.local/state/dynamicbrowser/`) before changing defaults. Query and set each scheme using `xdg-mime` in the user's desktop session; verify effective associations after changes. Obtain confirmation before changing defaults. Preserve the snapshot on partial failure and restore only entries still pointing to dynamicbrowser. Do not edit system files or replace a user's `mimeapps.list` wholesale. Test the command boundary with fixtures before running it in a disposable desktop session.
- Keep the existing Linux tray and IPC. Move platform-dependent tray dispatch and restart decisions out of shared orchestration as part of the tray work, preserving Windows behavior. Require a StatusNotifierItem host for Linux tray mode and use XDG autostart for sign-in. No host must not block on-demand routing. Treat source metadata as unknown for desktop launches that only pass URLs. Use KDE Plasma on Wayland as the initial desktop acceptance baseline; only advertise other desktops as verified after live checks. Document `xdg-utils`, the tray host, and the prerequisites for desktop error dialogs.
- Keep native CI jobs independent. Use the existing Windows ZIP workflow and add a Linux tarball job with the same version and checksum contract. Headless CI checks the package and stubbed registration behavior; desktop acceptance verifies actual system link activation and recovery on disposable sessions, not on the CI runner's host.

# Trade-offs

One configuration format and one version keep the targets aligned. Per-user XDG paths allow read-only Linux installs without changing portable Windows setups. An archive is sufficient for the initial Linux target; package-manager integration and desktop-specific source capture can be evaluated separately.
